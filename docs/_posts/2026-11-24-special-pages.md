> 한 줄 요약: 기쁘띠콘의 특별 페이지 두 개가 **어떤 문제를 풀려고** 만들어졌고, Flask 라우트와 Jinja2 템플릿으로 **어떻게 동작하는지** 설명합니다.

## 1. 왜 필요했나

기쁘띠콘은 안 쓰는 기프티콘을 이화인끼리 사고파는 중고 거래 마켓입니다. 상품 목록·상세·등록·리뷰만 있으면 "중고 거래 사이트"의 기본 흐름은 완성되지만, 팀 회의에서 두 가지 불편이 계속 나왔습니다.

1. **사는 사람 입장**: 상품이 많아지면 "오늘 점심에 쓸 만한 만 원 이하 기프티콘"을 고르려고 목록을 계속 넘겨야 합니다. 고르는 것 자체가 귀찮습니다.
2. **산 다음**: 기프티콘을 샀는데 어디서 다시 보는지, 유효기간이 언제까지인지 한눈에 볼 곳이 없습니다. 기프티콘은 유효기간이 지나면 그대로 돈을 잃는 상품이라 이게 특히 중요했습니다.

그래서 기쁘띠콘만의 특별 페이지로 **고르는 고민을 줄여 주는 "오늘 뭐 먹지?"**와, **산 기프티콘을 잊지 않게 해 주는 "내 기프티콘함"**을 만들었습니다.

## 2. 오늘 뭐 먹지? (`/today`, `/today/result`)

![오늘 뭐 먹지? 조건 선택 화면]({{ '/assets/images/special-today.png' | relative_url }})

화면 위쪽에서 **예산**(전체, 5,000원 미만, 5,000~10,000원 미만 …)과 **카테고리**(카페·베이커리, 치킨·피자·버거, 편의점 …)를 칩으로 고르고, 가운데 **룰렛 돌리기** 버튼을 누르면 조건에 맞는 상품 하나를 골라 줍니다.

### 조건은 URL 쿼리로만 주고받는다

칩은 버튼이 아니라 링크입니다. 예산 칩을 누르면 `/today?budget=5-10&category=편의점` 같은 주소로 이동하고, 서버는 쿼리 값을 읽어 후보를 다시 계산합니다. 자바스크립트 없이 동작하고, 주소를 복사하면 같은 조건이 그대로 열린다는 장점이 있습니다.

예산 구간은 `app.py`에 `(키, 표시 이름, 최소 이상, 최대 미만)` 형태로 한 번만 정의하고, 화면의 칩도 이 목록을 그대로 돌면서 그립니다.

```python
BUDGETS = [
    ("all", "전체", 0, None),
    ("u5", "5,000원 미만", 0, 5000),
    ("5-10", "5,000 ~ 10,000원 미만", 5000, 10000),
    ...
]
```

### 후보는 Firebase에 있는 "지금 살 수 있는" 상품만

두 화면(돌리기 전·후)이 같은 조건 계산을 쓰기 때문에 `special_context()` 함수 하나로 묶었습니다. 핵심은 후보를 거르는 부분입니다.

```python
candidates = [
    i for i in load_items()                       # Firebase item 노드 전체
    if i["status"] == "selling"                   # 판매 중인 것만
    and (i["dday"] is None or i["dday"] >= 0)     # 유효기간이 안 지난 것만
    and i["price"] >= budget[2]
    and (budget[3] is None or i["price"] < budget[3])
    and (not category or i["category"] == category)
]
```

`load_items()`는 상품 목록 화면과 같은 함수라서, 누군가 상품을 새로 등록하면 별도 작업 없이 바로 추천 후보에 들어갑니다. 예약 중·판매 완료 상품이나 유효기간이 지난 상품을 추천하면 사용자가 상세 페이지까지 갔다가 실망하게 되므로 여기서 먼저 걸러 냅니다. 잘못된 쿼리 값(`budget=abc`)이 들어와도 기본 구간으로 돌아가도록 처리했습니다.

### 결과 화면

![오늘 뭐 먹지? 추천 결과 화면]({{ '/assets/images/special-today-result.png' | relative_url }})

`/today/result`는 후보 중 하나를 `random.choice()`로 뽑아 룰렛 맨 위 칸에 사진을 넣고, 오른쪽에 상품 카드를 보여 줍니다. 예산 상한이 있으면 `상한 - 가격`을 계산해 **"800원 여유 있어요"**처럼 남는 돈도 알려 줍니다. 후보가 하나도 없으면 결과 화면 대신 조건 선택 화면을 다시 보여 주고, 버튼도 비활성화됩니다.

템플릿은 `special_result.html`이 `special.html`을 **상속(extends)**해서 룰렛 가운데 글자와 추천 칸 블록만 바꿉니다. 덕분에 조건 칩과 배너 코드를 두 번 쓰지 않아도 됩니다. 결과 카드의 **상품 상세 보기** 버튼은 `/view_detail/<상품명>`으로, **조건에 맞는 상품 더 보기**는 같은 카테고리의 판매 중 상품 목록으로 이어집니다.

## 3. 내 기프티콘함 (`/my_gifticons`)

![내 기프티콘함 화면]({{ '/assets/images/special-my-gifticons.png' | relative_url }})

내 기프티콘함은 **로그인한 구매자 본인만** 볼 수 있는 화면입니다. 세션에 아이디가 없으면 로그인 화면으로 보내고, 로그인한 뒤에는 원래 보려던 이 화면으로 돌아옵니다.

```python
@app.route("/my_gifticons")
def view_my_gifticons():
    if not session.get("id"):
        return login_redirect("내 기프티콘함은 로그인 후 볼 수 있어요.")
```

화면은 위에서부터 네 부분으로 나뉩니다.

- **요약 카드**: 사용 가능 개수, 3일 안에 만료되는 개수, 사용 완료 개수, 정가 대비 아낀 금액(`정가 - 결제 금액`의 합)
- **만료 임박 알림**: D-3 이하인 기프티콘이 있으면 빨간 띠로 "잊지 말고 사용하세요"를 띄웁니다. 문장 속 조사(이/가)는 상품명의 마지막 글자 받침을 계산해서 자연스럽게 붙입니다.
- **기프티콘 카드**: 전체·사용 가능·사용 완료 탭(`?tab=`)으로 거르고, 사용 가능한 것을 먼저, 그 안에서는 남은 날이 적은 순으로 정렬합니다. 카드마다 바코드와 **리뷰 쓰기** 버튼이 있는데, 리뷰 쓰기를 누르면 상품명이 미리 채워진 리뷰 작성 화면(`/reg_reviews?item=<상품명>`)으로 이동합니다.
- **구매 내역 표**: 구매일 최신순

바코드는 이미지가 아니라 **기프티콘 번호로 막대 굵기 46개를 계산해서** HTML로 그립니다. 같은 번호면 항상 같은 모양이 나오기 때문에 새로 고쳐도 바코드가 바뀌지 않습니다. **바코드 크게 보기**는 HTML `<dialog>` 요소의 `showModal()`로 띄워서, 매장에서 점원에게 보여 주기 쉽게 했습니다.

> 현재 내 기프티콘함의 구매 목록은 `app.py`의 샘플 데이터(`MY_GIFTICONS`)를 씁니다. 구매하기 기능이 DB에 구매자 정보를 기록하게 되면, 이 목록을 로그인한 사용자의 구매 기록으로 바꾸는 것이 다음 단계입니다.

## 4. 정리

- **같은 데이터, 다른 질문**: "오늘 뭐 먹지?"는 새 테이블을 만들지 않고 상품 목록과 같은 `load_items()`에 조건만 다르게 걸었습니다. 기능을 추가할 때 데이터를 새로 만들기보다 이미 있는 데이터에 어떤 질문을 던질지 먼저 생각하게 됐습니다.
- **상태는 URL에**: 조건·탭을 쿼리 문자열로 두니 서버 코드가 단순해지고, 뒤로 가기와 링크 공유가 자연스럽게 동작했습니다.
- **템플릿 상속**: 전·후 화면처럼 대부분이 같은 화면은 `extends`와 `block`으로 다른 부분만 바꾸는 것이 유지보수에 훨씬 편했습니다.
- **다음에 개선할 점**: 내 기프티콘함을 실제 구매 기록과 연결하고, "사용 완료 처리" 버튼이 DB 상태를 바꾸도록 하는 것.
