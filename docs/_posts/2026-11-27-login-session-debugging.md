> 한 줄 요약: 기쁘띠콘의 로그인 기능을 중심으로 **세션 키 불일치가 발생하는 원인과 해결 방법**, 비밀번호 검증 및 로그인 실패 처리 과정을 정리합니다.

## 1. 왜 필요했나

기쁘띠콘은 안 쓰는 기프티콘을 이화인끼리 사고파는 중고 거래 마켓입니다. 로그인하지 않은 상태에서 웹사이트에 접속하면 상품 목록 페이지가 표시되며, 상품 목록과 상세 페이지를 자유롭게 둘러볼 수 있습니다. 다만 상품 등록이나 리뷰 작성, 좋아요와 같이 사용자를 구분해야 하는 기능을 이용하려면 로그인이 필요합니다.

이때 단순히 아이디와 비밀번호가 일치하는지 확인하는 것만으로는 충분하지 않습니다. 로그인에 성공한 이후 다른 페이지로 이동하더라도 서버가 현재 사용자를 알아볼 수 있어야 하기 때문입니다. 기쁘띠콘에서는 이를 위해 Flask의 `session`을 사용합니다.

여러 팀원이 각각의 페이지를 개발하는 과정에서는 로그인 상태를 확인하는 코드가 여러 파일에 존재하게 됩니다. 이때 로그인 정보를 저장하는 세션 키와 다른 페이지에서 확인하는 세션 키가 다르면, 정상적으로 로그인했더라도 로그인하지 않은 사용자로 처리될 수 있습니다.

이번 글에서는 이러한 세션 키 불일치 문제를 중심으로 로그인 과정에서 확인해야 할 부분과 해결 방법을 살펴봅니다.

## 2. 로그인·세션 디버깅 과정

### ① 로그인 상태는 어떻게 유지할까?

HTTP는 기본적으로 이전 요청의 상태를 기억하지 않는 비상태성(stateless) 프로토콜입니다. 따라서 로그인 요청에 성공했더라도 다음 페이지를 요청할 때 별도의 상태 관리가 없다면 서버는 같은 사용자인지 구분하기 어렵습니다.

Flask에서는 `session`을 이용해 여러 요청에 걸쳐 사용자 정보를 유지할 수 있습니다. 기쁘띠콘은 로그인에 성공한 사용자의 아이디를 세션에 저장하고, 다른 페이지에서는 해당 값을 확인하여 로그인 여부를 판단합니다.

전체 로그인 흐름은 다음과 같습니다.

| 순서 | 처리 과정 | 관련 파일 |
|---|---|---|
| ① | 아이디와 비밀번호 입력 | `templates/login.html` |
| ② | 입력한 비밀번호를 해시값으로 변환 | `app.py` |
| ③ | Firebase에 저장된 회원 정보와 비교 | `database.py` |
| ④ | 로그인 성공 시 세션에 아이디 저장 | `app.py` |
| ⑤ | 다른 페이지에서 세션을 확인 | `app.py`, `templates/` |
| ⑥ | 로그아웃 시 세션 삭제 | `app.py` |

### ② 세션 키 불일치 문제

로그인 상태가 올바르게 인식되지 않을 때는 먼저 세션에 값을 저장하는 부분과 값을 읽는 부분을 비교해야 합니다.

다음은 세션 키가 일치하지 않는 상황을 보여 주는 예시입니다.

```python
# 로그인 성공 시
session["user_id"] = id_

# 상품 등록 페이지에서 로그인 여부 확인
if not session.get("id"):
    return redirect(url_for("login"))
```

로그인에 성공하면 사용자 아이디가 `user_id`라는 키에 저장됩니다. 하지만 상품 등록 페이지에서는 `id`라는 다른 키를 확인하고 있습니다.

Flask의 세션은 딕셔너리와 비슷한 방식으로 값을 관리하므로 `user_id`와 `id`는 서로 다른 키입니다. 따라서 `id`라는 키에 값이 저장되어 있지 않다면 `session.get("id")`는 `None`을 반환합니다.

이 경우 아이디와 비밀번호 검증에 성공했더라도 상품 등록 페이지에서는 로그인하지 않은 사용자로 판단하게 됩니다. 사용자는 로그인을 완료했는데도 다시 로그인 화면으로 이동하는 상황을 겪을 수 있습니다.

이러한 문제는 회원 정보가 Firebase에 정상적으로 저장되어 있는지 확인하는 것만으로는 찾기 어렵습니다. **데이터베이스에서 회원 정보를 검증하는 과정과 로그인 이후 세션을 확인하는 과정은 서로 구분해서 살펴봐야 합니다.**

### ③ 세션 키를 `id`로 통일하기

기쁘띠콘의 현재 코드에서는 로그인한 사용자의 아이디를 `session["id"]`에 저장합니다.

`app.py`의 `login_confirm()`에서 로그인에 성공했을 때 실행되는 부분입니다.

```python
if DB.find_user(id_, pw_hash):
    session["id"] = id_
    return redirect(next_url or url_for("home_logged_in"))
```

회원 정보가 일치하면 세션에 아이디를 저장하고, 로그인 이후 이동할 페이지로 연결합니다.

상품 등록 페이지에서도 동일한 `id` 키를 사용합니다.

```python
@app.route("/reg_items")
def reg_item():
    if not session.get("id"):
        return login_redirect(
            "기프티콘을 판매하려면 로그인해 주세요."
        )

    user = DB.get_user(session["id"]) or {}
    return render_template(
        "reg_items.html",
        categories=CATEGORIES,
        seller=session["id"],
        seller_email=user.get("email", "")
    )
```

세션에 아이디가 없으면 로그인 화면으로 이동하고, 아이디가 존재하면 해당 사용자의 회원 정보를 조회하여 상품 등록 화면에 전달합니다.

이렇게 세션 키를 통일하면 로그인 여부를 일관되게 판단할 수 있을 뿐만 아니라, 상품 등록 시 판매자 아이디를 현재 로그인한 계정의 정보로 자동 입력할 수 있습니다.

이메일은 회원 정보에 등록된 값이 있으면 자동으로 입력되며, 이메일 정보가 없는 기존 계정의 경우에는 사용자가 직접 입력하도록 예외 처리를 적용했습니다. 직접 입력하는 경우에도 이화여자대학교 이메일(@ewha.ac.kr 또는 @ewhain.net)만 사용할 수 있도록 서버에서 검증합니다.

리뷰 작성과 좋아요 기능에서도 같은 세션 키를 사용하기 때문에 여러 페이지에서 동일한 사용자를 기준으로 기능을 처리할 수 있습니다.

**디버깅 팁:** 세션 관련 문제를 확인할 때는 VS Code의 전체 검색 기능(`Ctrl + Shift + F`)을 이용해 `session["user_id"]`, `session["id"]`, `session.get("id")` 등을 검색하면 저장하는 부분과 읽는 부분이 일치하는지 효율적으로 확인할 수 있습니다. Python 코드뿐만 아니라 로그인 상태에 따라 화면을 다르게 표시하는 HTML 템플릿도 함께 확인하는 것이 좋습니다.

### ④ 비밀번호 해시값 비교하기

세션 키가 일치하더라도 로그인 검증 자체에 실패하면 로그인 성공에 따른 세션 저장이 이루어지지 않습니다. 따라서 로그인 상태에 문제가 있을 때는 회원가입과 로그인 과정에서 비밀번호를 어떻게 처리하는지도 확인해야 합니다.

기쁘띠콘에서는 비밀번호를 원문 그대로 Firebase에 저장하지 않고 SHA-256 해시값으로 변환하여 저장합니다.

회원가입을 처리하는 `register_user()`의 핵심 코드는 다음과 같습니다.

```python
pw_hash = hashlib.sha256(
    pw.encode("utf-8")
).hexdigest()

if DB.insert_user(data, pw_hash):
    flash("회원가입이 완료되었어요. 로그인해 주세요.")
    return redirect(url_for("login"))
```

입력한 비밀번호를 UTF-8로 인코딩한 뒤 SHA-256 해시 함수에 전달합니다. `hexdigest()`를 사용하면 계산된 해시값을 16진수 문자열로 얻을 수 있습니다.

로그인할 때도 회원가입과 동일한 방식으로 입력한 비밀번호를 변환합니다.

```python
pw_hash = hashlib.sha256(
    pw.encode("utf-8")
).hexdigest()

if DB.find_user(id_, pw_hash):
    session["id"] = id_
    return redirect(next_url or url_for("home_logged_in"))
```

`database.py`의 `find_user()`는 Firebase에 저장된 회원 정보에서 아이디와 비밀번호 해시값이 모두 일치하는 회원이 있는지 확인합니다.

```python
def find_user(self, id_, pw_hash):
    users = self.db.child("user").get()
    if users.val() is None:
        return False

    for res in users.each():
        value = res.val()
        if (
            isinstance(value, dict)
            and value.get('id') == id_
            and value.get('pw') == pw_hash
        ):
            return True

    return False
```

회원가입과 로그인에서 동일한 해시 방식을 사용해야 올바른 비밀번호를 입력했을 때 저장된 해시값과 일치합니다.

만약 회원가입에서는 해시값을 저장하고 로그인에서는 입력한 비밀번호 원문을 그대로 비교한다면, 사용자가 올바른 비밀번호를 입력하더라도 검증에 실패하게 됩니다.

따라서 로그인에 실패하는 경우에는 세션뿐만 아니라 회원가입과 로그인에서 비밀번호를 처리하는 방식이 동일한지, 데이터베이스에서 올바른 필드를 비교하는지도 확인해야 합니다.

### ⑤ 로그인 실패 시 `flash()` 메시지 전달하기

로그인 검증에 실패했을 때 아무런 안내 없이 로그인 화면만 다시 표시되면 사용자는 실패 원인을 파악하기 어렵습니다.

기쁘띠콘에서는 Flask의 `flash()`를 이용해 로그인 실패 메시지를 전달합니다.

```python
flash("Wrong ID or PW!")
return render_template(
    "login.html",
    next=next_url or ""
)
```

`flash()`는 사용자에게 전달할 일회성 메시지를 저장하는 Flask의 기능입니다. 기쁘띠콘에서는 전달받은 메시지를 브라우저 경고창으로 표시합니다.

![로그인 실패 시 오류 메시지]({{ '/assets/images/login-debug-failed.png' | relative_url }})

실제로 가입된 계정의 아이디와 잘못된 비밀번호를 입력하여 로그인했을 때, "Wrong ID or PW!"라는 경고창이 표시되는 것을 확인했습니다. 사용자는 이 안내를 통해 아이디 또는 비밀번호를 다시 확인할 수 있습니다.

아이디가 존재하지 않는 경우와 비밀번호가 일치하지 않는 경우에 동일한 메시지를 사용하는 것도 중요합니다. 로그인 실패 원인을 지나치게 구체적으로 알려 주면 다른 사람이 특정 아이디의 가입 여부를 알아낼 수 있기 때문입니다.

### ⑥ 로그인이 필요한 페이지로 다시 돌아오기

기쁘띠콘에서는 로그인하지 않은 상태에서도 상품 목록을 둘러볼 수 있습니다. 그러나 상품 목록 페이지에서 판매하기 버튼을 클릭하면 로그인 안내 메시지가 표시되고 로그인 페이지로 이동합니다.

이때 로그인에 성공한 뒤 항상 홈 화면으로 이동한다면 사용자는 상품을 등록하기 위해 판매하기 버튼을 다시 눌러야 합니다.

기쁘띠콘에서는 이러한 불편을 줄이기 위해 `login_redirect()`를 이용하여 원래 접근하려던 주소를 `next`라는 값으로 전달합니다.

```python
def login_redirect(message="로그인이 필요한 페이지예요."):
    flash(message)
    return redirect(
        url_for("login", next=request.full_path.rstrip("?"))
    )
```

`request.full_path`는 현재 요청의 경로와 쿼리 문자열을 가져옵니다. 이를 `next` 값으로 전달하면 로그인 화면에서도 사용자가 원래 접근하려던 주소를 유지할 수 있습니다.

로그인 화면에서는 전달받은 `next` 값을 숨겨진 입력 필드에 보관합니다.

{% raw %}
```html
{% if next %}
<input type="hidden" name="next" value="{{ next }}">
{% endif %}
```
{% endraw %}

로그인에 성공하면 해당 주소로 이동하고, 돌아갈 주소가 없는 경우에는 기본 홈 화면으로 이동합니다.

```python
return redirect(
    next_url or url_for("home_logged_in")
)
```

이 과정에서 `safe_next_url()`을 통해 돌아갈 주소가 내부 경로 형태인지 확인합니다. 외부 주소나 `//`로 시작하는 주소는 허용하지 않도록 처리하여 외부 사이트로의 의도하지 않은 이동을 제한합니다.

![비로그인 상태에서 판매하기 버튼 클릭 시 안내 메시지]({{ '/assets/images/login-debug-required.png' | relative_url }})

실제로 로그인하지 않은 상태에서 상품 목록 페이지의 판매하기 버튼을 클릭하여 테스트했습니다. 이때 "기프티콘을 판매하려면 로그인해 주세요."라는 안내 메시지가 표시되었으며, 확인 버튼을 누르면 로그인 페이지로 이동했습니다.

이후 올바른 아이디와 비밀번호를 입력하여 로그인하자 기본 홈 화면이 아닌 상품 등록 페이지로 이동하는 것을 확인했습니다.

실제 화면 이동 순서는 다음과 같습니다.

**상품 목록 → 판매하기 버튼 클릭 → 로그인 안내 경고창 → 로그인 페이지 → 상품 등록 페이지**

이를 통해 비로그인 사용자의 접근을 제한하면서도 로그인 이후 사용자가 원래 이용하려던 기능을 이어서 사용할 수 있음을 확인했습니다. 별도로 상품 목록으로 돌아가 판매하기 버튼을 다시 누를 필요가 없다는 점에서 사용자 편의성도 높일 수 있습니다.

## 3. 결과

### 로그인 성공 및 사용자 정보 표시

![로그인 성공 화면]({{ '/assets/images/login-debug-success.png' | relative_url }})

일반적인 로그인 과정에서는 로그인 검증에 성공하면 사용자 아이디를 세션에 저장하고 로그인 전용 홈 화면으로 이동합니다.

홈 화면의 환영 문구와 상단 헤더에 현재 로그인한 사용자의 아이디가 표시되며, 판매하기와 리뷰 작성 등 로그인이 필요한 기능을 이용할 수 있습니다.

로그인 이전에 접근하려던 페이지가 있다면 홈 화면 대신 해당 페이지로 이동합니다.

### 로그인한 계정의 판매자 정보

![상품 등록 화면의 판매자 정보]({{ '/assets/images/login-debug-seller.png' | relative_url }})

상품 등록 화면에서는 세션에 저장된 아이디를 판매자 ID로 자동 입력하고, 사용자가 임의로 수정할 수 없도록 처리합니다.

위 화면은 이메일 정보가 등록되지 않은 기존 계정으로 로그인한 경우입니다. 판매자 ID에는 현재 로그인한 계정의 아이디가 표시되며, 이메일 입력란에는 `example@ewha.ac.kr`이라는 입력 예시가 표시됩니다. 사용자는 해당 입력란에 자신의 학교 이메일을 직접 입력해야 합니다.

회원 정보에 이메일이 등록되어 있다면 해당 이메일도 자동 입력되며 수정할 수 없습니다.

실제 상품 등록 과정에서도 폼에서 전달받은 판매자 ID가 아닌 세션에 저장된 아이디를 사용합니다.

```python
user = DB.get_user(session["id"]) or {}
data["seller"] = session["id"]
data["email"] = user.get("email") or request.form.get("email", "").strip()
```

HTML에서 판매자 ID를 수정하지 못하도록 설정하는 것뿐만 아니라, 서버에서도 세션에 저장된 아이디를 사용하여 판매자를 결정합니다. 이를 통해 폼의 값을 임의로 조작하여 다른 사용자의 아이디로 상품을 등록하는 것을 방지할 수 있습니다.

### 로그아웃 및 접근 제한

로그아웃 시에는 `session.clear()`를 사용하여 세션 정보를 삭제합니다.

```python
@app.route("/logout")
def logout():
    session.clear()
    return redirect(url_for("view_list"))
```

로그아웃하면 세션 정보를 삭제하고 상품 목록 페이지로 이동합니다. 상품 목록과 상세 페이지는 계속 이용할 수 있지만, 판매하기와 같이 로그인이 필요한 기능에 접근하면 다시 로그인 안내 메시지가 표시됩니다.

### 테스트 결과 한눈에 보기

| 테스트 상황 | 실행 결과 |
|---|---|
| 비로그인 상태에서 상품 목록 이용 | 상품 목록 정상 표시 |
| 올바른 아이디와 비밀번호 입력 | 로그인 성공 및 홈 화면 이동 |
| 잘못된 비밀번호 입력 | 로그인 실패 경고창 표시 |
| 로그인 후 판매하기 버튼 클릭 | 상품 등록 화면 이동 |
| 상품 등록 화면의 판매자 ID 확인 | 현재 로그인한 계정의 아이디 자동 입력 |
| 로그아웃 후 판매하기 버튼 클릭 | 로그인 안내 경고창 표시 |
| 로그인 안내 후 정상 로그인 | 기존에 접근하려던 상품 등록 화면으로 이동 |

로그인 성공과 실패, 세션을 이용한 사용자 정보 표시, 비로그인 사용자의 접근 제한, 로그인 후 기존 페이지 복귀까지 확인했습니다.

## 4. 정리

이번 로그인·세션 기능을 통해 로그인 검증에 성공하는 것과 이후 페이지에서 로그인 상태를 올바르게 유지하는 것은 서로 다른 과정이라는 점을 확인할 수 있었습니다.

### 배운 점

- **세션 키의 일관성:** 여러 팀원이 각각의 기능을 구현하는 프로젝트에서는 세션 키처럼 공통으로 사용하는 값을 미리 정하고 일관되게 사용하는 것이 중요합니다. 작은 변수명 차이도 상품 등록이나 리뷰 작성 등 다른 기능의 동작에 영향을 줄 수 있습니다.
- **로그인 검증과 세션 관리의 구분:** 로그인에 실패하는 경우에는 비밀번호 해시 비교를 확인하고, 로그인에 성공했는데 다른 페이지에서 로그인 상태를 인식하지 못하는 경우에는 세션을 저장하고 읽는 부분을 확인해야 합니다.
- **사용자 편의성을 고려한 오류 처리:** 로그인 실패 메시지와 로그인 이후의 이동 경로를 함께 처리하면 사용자가 문제 상황을 이해하고 원래 이용하려던 기능을 이어서 사용할 수 있습니다.
- **서버에서의 사용자 정보 검증:** 판매자 아이디처럼 현재 로그인한 사용자와 관련된 정보는 폼에서 전달받은 값을 그대로 신뢰하기보다 서버의 세션 정보를 기준으로 처리하는 것이 중요합니다.

### 다음에 개선할 점

현재 프로젝트는 비밀번호를 SHA-256으로 변환하여 저장하고 있지만, SHA-256 단독 사용은 실제 서비스의 비밀번호 저장 방식으로는 충분하지 않습니다. 계산 속도가 빠르고 별도의 솔트를 사용하지 않기 때문에 비밀번호 추측 공격에 취약할 수 있습니다.

향후에는 Werkzeug의 `generate_password_hash()`와 `check_password_hash()`를 활용하여 솔트와 비밀번호 저장에 적합한 해시 알고리즘을 적용하는 방향으로 개선할 수 있습니다.

또한 로그인 성공과 실패, 세션 유지, 로그아웃, 로그인 필수 페이지 접근 등의 상황을 자동으로 검사하는 테스트 코드를 작성하면 이후 다른 기능을 추가하거나 수정할 때 로그인 관련 문제가 다시 발생하는 것을 확인하는 데 도움이 될 것입니다.
